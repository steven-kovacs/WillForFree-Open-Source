# Optional AI help

The guided interview runs in the browser. Ordinary answers, documents and free-text questions are never sent to the model. Prepared help covers common questions, reads the actual kit type, and includes a translated topic menu. An unmatched question gets an explicit fallback. For an ambiguous request for general help, the endpoint can choose one of the supplied topic labels. Its model output has a 64-token ceiling. The browser reuses a successful topic choice for the same set of labels and kind of step during that chat.

The **AI Enabled** switch stays in the chat toolbar, including in full screen. It opens the same explanation as Free & private. Only **Turn Off** or **Turn On** changes the setting; Back to chat, Close and Escape leave it alone. **Use without AI** on the privacy page switches it off directly. The [chat control](../public/chat-ai.js) remembers only the on/off choice in this tab’s session storage. The interview and kit work either way. Opening the dialog makes no AI request, and disabling AI aborts an outstanding browser request and prevents its result from being used.

The UI limits ordinary questions to 240 characters. Short step hints aim for 60 words and keep the complete translation when an excerpt would fall back to English. Prepared answers retain their full wording, including conditions that distinguish printed, handwritten and notes-only routes. The form accepts longer local notes (600 characters) and lists of names (650). [Question coverage, language checks and sources](review/interview-help.md)

## Limits

The endpoint checks every POST before reading the body, including cache hits and malformed submissions. JSON payloads are limited to 512 bytes. The server issues a signed, HTTP-only, SameSite first-party cookie scoped to the helper. It expires after 24 hours. A browser may make 3 requests in a rolling minute and 8 in a rolling hour. A network may make 18 in a minute and 40 in an hour. IPv4 addresses and IPv6 /64 prefixes are protected with a keyed digest. The store holds only coded keys, recent timestamps and expiry. A visitor behind a shared network can share its limit with others.

An atomic, shared reservation limits the provider to 24 attempts in any rolling hour. Identical requests in one server share in-flight work and successful cached responses. A browser that receives 429 follows Retry-After and uses local help until the cooldown ends. A quota store outage falls back to local help. Neither condition prevents answering the interview or downloading.

## Operations

The loopback preview uses the socket address and can run with in-memory counters. The Cloud Run entry point is `node help-backend.mjs`. Its production configuration requires the provider key, a shared signing secret of at least 32 bytes, a Firestore project and an HTTPS consumer origin. All replicas use Application Default Credentials and the same Firestore database. `WFF_HELP_DATABASE` selects a named database and `WFF_HELP_LOG_PROJECT` selects the notifier's project. Their defaults are the default database and the configured Firestore project. A request that cannot reserve quota receives local help. Expired records stop counting immediately and are pruned during requests using conditional deletes.

The HTTPS helper issues a signed `__session` cookie with `Secure`, `HttpOnly`, `SameSite=Strict` and `Path=/api/topic`. Firebase Hosting forwards this cookie to dynamic backends. Helper responses use `private, no-store`. [Firebase Hosting cookie handling](https://firebase.google.com/docs/hosting/manage-cache#using_cookies)

`WFF_HELP_NETWORK_SOURCE=direct-ticket` uses two requests when the visitor needs remote topic selection. First the browser fetches `GET /api/network-ticket` directly from the Google service origin with no cookies, referrer or topics. The service reads the last address appended by the direct Cloud Run frontend and returns an authenticated, randomly encrypted proof that expires after two minutes. Its contents are opaque to the browser. Then the browser posts its topic labels to `/api/topic` on the consumer site, attaching the proof and its first-party cookie. Firebase rewrites only that POST path to Cloud Run. The service verifies the proof and uses the resulting IPv4 address or IPv6 prefix for its keyed counter. Verification of a missing, altered or expired proof stops the request before a model call. A CDN in front of the ticket endpoint would group users behind that CDN. [Cloud Run direct frontend behavior](https://github.com/GoogleCloudPlatform/nodejs-docs-samples/issues/3583) · [Firebase rewrite configuration](https://firebase.google.com/docs/hosting/cloud-run)

For a deployment using this mode, set the real consumer origin in `WFF_HELP_ORIGIN`, set `networkTicketURL` in the staged `public/release-target.js` to the direct HTTPS ticket endpoint and allow that origin in the consumer's `connect-src`. Set the topic flag in the staged runtime and route the consumer's `/api/topic` to the same service. A plain `shared` deployment has one combined network allowance. The alternative `trusted-edge` mode accepts a single address from an ingress that overwrites `X-Wff-Client-IP` and controls access to the service.

The backend waits for a bounded Cloud Logging write before completing a newly limited request. The private `willforfree-ai-abuse` event contains only its event type and an allowlisted reason. Concurrent refusals share an in-flight write, and a failed write can retry on a later refusal after one minute. The notifier polls every five minutes and groups events into at most one email per hour. Its email contains the limit types and latest event time. Managed Cloud Run request logs have a separate retention policy. [Cloud Run logging](https://docs.cloud.google.com/run/docs/logging)
